# Plan: Convert Starter to Cookiecutter Template

**Goal:** Turn `company-website-starter` into a reusable cookiecutter template so each new client site (e.g. chess club, law firm, NGO) is generated as a fresh repo with the generic starter as its foundation, then extended with domain-specific apps.

---

## How cookiecutter works

```
cookiecutter gh:your-org/company-website-starter
# prompts:
#   project_name    → "UCF Chess Club"
#   project_slug    → "ucf_chess"     (Django package name)
#   site_name       → "UCF Chess Club"
#   primary_color   → "#4f46e5"
#   author_email    → "admin@ucfchess.org"
#
# outputs a ready-to-run Django project at ./ucf_chess/
```

---

## `cookiecutter.json` (root of template repo)

```json
{
  "project_name":    "My Company",
  "project_slug":    "{{ cookiecutter.project_name.lower().replace(' ', '_').replace('-', '_') }}",
  "site_name":       "{{ cookiecutter.project_name }}",
  "primary_color":   "#4f46e5",
  "author_email":    "admin@example.com",
  "python_version":  "3.11",
  "django_version":  "5.2"
}
```

## What needs to change in the repo

### 1. Rename the project package

The Django project is currently in `project/`. This needs to become `{{cookiecutter.project_slug}}/` so the generated project has a unique package name.

Files that reference `project.`:
- `manage.py` — `DJANGO_SETTINGS_MODULE`
- `project/settings/base.py` — `ROOT_URLCONF`, `WSGI_APPLICATION`, `templatetags`
- `project/wsgi.py`, `project/asgi.py`
- All app `apps.py` files that import from `project`

After renaming, replace every literal `project.` with `{{cookiecutter.project_slug}}.`.

### 2. Parameterise `input.css` primary color

```css
/* currently hardcoded */
--color-primary: #4f46e5;

/* becomes */
--color-primary: {{ cookiecutter.primary_color }};
```

Run Tailwind compile in the post-gen hook so `output.css` is generated fresh.

### 3. Parameterise `SiteConfig` fixture / initial data migration

Instead of the current hardcoded fixture, generate it from template variables:

```json
[{
  "model": "core.siteconfig",
  "fields": {
    "site_name": "{{ cookiecutter.site_name }}",
    "email":     "{{ cookiecutter.author_email }}"
  }
}]
```

### 4. Add `cookiecutter.json` to repo root

### 5. Add `hooks/post_gen_project.py`

```python
import subprocess, os

# Install dependencies
subprocess.run(['pip', 'install', '-r', 'requirements.txt'], check=True)

# Run migrations
subprocess.run(['python', 'manage.py', 'migrate'], check=True)

# Load initial SiteConfig
subprocess.run(['python', 'manage.py', 'loaddata', 'fixtures/initial.json'], check=True)

# Compile Tailwind
subprocess.run(['bin/tailwindcss', '-i', 'styling/static_src/input.css',
                '-o', 'templates/css/output.css', '--minify'], check=True)

print("\n✅ Project ready. Run: python manage.py runserver")
```

### 6. `.gitignore` additions

Add `cookiecutter.json` baking artefacts and ensure `output.css` is excluded from the template (generated by post-gen hook).

```
├── hooks/
│   └── post_gen_project.py
└── {{cookiecutter.project_slug}}/    ← everything moves here
    ├── manage.py
    ├── {{cookiecutter.project_slug}}/   (was project/)
    │   ├── settings/
    │   ├── urls.py
    │   └── ...
    ├── core/
    ├── blog/
    ├── events/
    ├── ...
    └── requirements.txt
```

## Workflow for a new client site

```bash
# Generate the site
cookiecutter gh:your-org/company-website-starter

# Add domain-specific apps (e.g. chess)
cd ucf_chess
git init && git add . && git commit -m "init: generated from company-website-starter"
mkdir chess && ...
```

The client repo has zero knowledge of the template after generation — it's a plain Django project they own and extend freely.

---

## Upgrade path

If the starter template gets improvements (security patches, new section types), clients can cherry-pick commits or apply a diff manually. There is no automatic sync — that's intentional; client repos diverge.
